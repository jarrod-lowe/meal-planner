## 1. Conventions

| Thing           | Convention                                                                                             |
| --------------- | ------------------------------------------------------------------------------------------------------ |
| IDs             | UUIDv7 strings, generated by the client. Cognito users are identified by `sub`.                        |
| Local date      | `LocalDate`: `"YYYY-MM-DD"`                                                                            |
| Local date-time | `LocalDateTime`: `"YYYY-MM-DDTHH:mm"`, holiday-local, no offset. Strings sort lexically in time order. |
| Time zone       | IANA name on the holiday (e.g. `"Pacific/Auckland"`). Used only to work out "now".                     |
| Quantities      | JavaScript `number` / Go `float64`. No rounding in storage or the engine.                              |
| Display         | Quantities shown with at most 2 decimal places, trailing zeros trimmed (`1.5`, `0.33`, `2`).           |
| Comparison      | The engine treats differences smaller than `EPSILON = 1e-9` as zero.                                   |
| JSON            | camelCase field names, in the API and in DynamoDB attributes.                                          |
| Versions        | Every stored item has an integer `version`, starting at 1.                                             |

## 2. Domain model

These TypeScript types live in `src/lib/model/`. They are generated from
`openapi.yaml` (see [§5](#5-api)), with the derived types written by hand. The
Go structs in `backend/internal/model` mirror them.

### 2.1 Fixed lists

```ts
// Order here is the order sections appear on a shopping list.
const SHOP_SECTIONS = [
  'produce', 'bakery', 'meat-fish', 'dairy', 'frozen',
  'pantry', 'drinks', 'household', 'other',
] as const;
type ShopSection = typeof SHOP_SECTIONS[number];

const MEAL_SLOTS = ['breakfast', 'lunch', 'dinner', 'snacks', 'other'] as const;
type MealSlot = typeof MEAL_SLOTS[number];

// UI defaults only; a mealtime can be at any time.
const SLOT_DEFAULT_TIMES: Record<MealSlot, string> = {
  breakfast: '08:00', lunch: '12:30', dinner: '18:30', snacks: '15:00', other: '12:00',
};
```

Shop sections are a fixed list (an OpenAPI enum) so that trips and ingredients
always agree. Display names come from i18n.

### 2.2 Stored facts

```ts
interface Versioned { version: number; updatedAt: string /* ISO UTC */; updatedBy: string /* sub */ }

interface Holiday extends Versioned {
  id: string;
  name: string;
  timeZone: string;
  startDate: LocalDate;   // planner grid range; events outside it are allowed but warned about
  endDate: LocalDate;
}

interface Member extends Versioned {
  userSub: string;        // the member's id; display name comes from GET /users
}

interface Attendee extends Versioned {
  id: string;
  name: string;
}

interface Meal extends Versioned {
  id: string;
  name: string;           // e.g. "Jan 1 Dinner", "Jan 1–5 Lunch"; suggested by the UI, editable
  slot: MealSlot;         // places the meal on the planner grid
  recipeId: string | null;
  mealtimes: Mealtime[];  // 1..n, embedded; sorted by `at`
}

interface Mealtime {
  id: string;
  at: LocalDateTime;
  attendeeIds: string[];  // servings = number of these that still exist
}

interface ShoppingTrip extends Versioned {
  id: string;
  name: string;               // e.g. "Big shop", "Corner dairy"
  at: LocalDateTime;
  sections: ShopSection[];    // default: all
  status: 'planned' | 'done';
}

type StockChange = ManualStockChange | Purchase;

interface ManualStockChange extends Versioned {
  id: string;
  kind: 'add' | 'remove';
  at: LocalDateTime;
  ingredientId: string;
  quantity: number;           // > 0
  note?: string;
}

interface Purchase extends Versioned {
  id: string;
  kind: 'purchase';
  tripId: string;             // happens at the trip's `at`; no time of its own
  ingredientId: string;
  quantity: number;           // > 0
}

interface Recipe extends Versioned {
  id: string;
  name: string;
  servings: number;           // > 0
  lines: { ingredientId: string; quantity: number }[];   // quantity > 0; an ingredient may appear once
  notes: string;              // free text: method, source, etc.
  deleted: boolean;
}

interface Ingredient extends Versioned {
  id: string;
  name: string;
  unit: string;               // free text, e.g. "g", "can", "box"
  shopSection: ShopSection;
  deleted: boolean;
}
```

### 2.3 Modelling decisions

- **One-off and generic meals have the same shape.** A one-off meal is a meal
  with one mealtime. The UI presents it as a single thing.
- **Dinner A and Dinner B** are two meals with the same slot and mealtimes at
  the same time. The grid shows them side by side; nothing else needs special
  handling.
- **A purchase has no time of its own.** It takes its trip's time, so moving a
  trip moves its purchases with it.
- **"Happened" is explicit.** A trip counts as happened when its `status` is
  `done` (the shopper taps *Finish trip*). Simply passing the trip's time
  doesn't change how it is processed; the UI prompts to finish trips whose time
  has passed (see warnings in [§3.6](#36-warnings)).
- **No cascading deletes.** Deleting an attendee, trip, recipe or ingredient
  leaves references to it in other items. The engine ignores dangling
  references (see [§3.2](#32-resolving-references)), and the UI warns before
  deleting something in use. IDs are never reused, so a dangling reference
  can't be revived by accident.
- **Catalogue deletes are soft**, so recipes and ingredients still resolve for
  old holidays. Holiday items are hard-deleted.
- **Duplicate ingredients** (same name *and* unit) are allowed by the server.
  The UI warns before creating one. Same name with a different unit is normal
  ("Cereal, box" vs "Cereal, kg").

## 3. Planning engine

`src/lib/engine/` is pure TypeScript. It must not import Svelte, the DOM, the
API client or any date library. It is one function plus small helpers:

```ts
function plan(facts: HolidayFacts, catalogue: Catalogue, now: LocalDateTime): Plan;

interface HolidayFacts {
  holiday: Holiday;
  attendees: Attendee[];
  meals: Meal[];
  trips: ShoppingTrip[];
  stockChanges: StockChange[];
}
interface Catalogue { recipes: Recipe[]; ingredients: Ingredient[] }
```

### 3.1 Output

```ts
interface Plan {
  consumption: Map<string /* mealtimeId */, ConsumptionLine[]>;
  shoppingLists: Map<string /* tripId */, ShoppingListLine[]>;
  shortfalls: Shortfall[];                    // sorted by time, then ingredient name
  stock: Map<string /* ingredientId */, StockEntry[]>;   // full timeline per ingredient
  warnings: Warning[];
}

interface ConsumptionLine { ingredientId: string; quantity: number }   // scaled

interface ShoppingListLine {
  ingredientId: string;
  listQuantity: number;      // what the plan says to buy (0 if only recorded, not listed)
  recordedQuantity: number;  // sum of purchases recorded against this trip
}

interface Shortfall {
  mealtimeId: string; mealId: string; ingredientId: string; at: LocalDateTime;
  needed: number; available: number; missing: number;
  past: boolean;             // at < now
}

interface StockEntry {
  at: LocalDateTime;
  source: { type: 'manual'; stockChangeId: string }
        | { type: 'trip'; tripId: string; assumed: boolean }  // assumed = planned trip
        | { type: 'mealtime'; mealtimeId: string; mealId: string };
  delta: number;             // signed; what actually moved
  balance: number;           // after this entry, never negative
}
```

Helper: `stockAt(plan, ingredientId, at)` gives the balance after every entry
at or before `at`. The stock view calls it with `now`.

### 3.2 Resolving references

| Reference                                  | When it can't be resolved                                                                              |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------ |
| `mealtime.attendeeIds[]` → attendee        | Not counted toward servings                                                                            |
| `meal.recipeId` → recipe                   | Soft-deleted: used normally. Missing: meal treated as having no recipe, plus warning `missing-recipe`. |
| `recipe.lines[].ingredientId` → ingredient | Soft-deleted: used normally. Missing: line skipped, plus warning `missing-ingredient`.                 |
| `stockChange.ingredientId` → ingredient    | Same as above                                                                                          |
| `purchase.tripId` → trip                   | Purchase ignored (an orphan of a deleted trip)                                                         |

### 3.3 Consumption

For each mealtime with a resolvable recipe:

```plain
servings = number of resolvable attendeeIds
factor   = servings / recipe.servings
consumption[line.ingredientId] = line.quantity × factor    (skipped when servings = 0)
```

### 3.4 Event ordering

Ingredients never interact, so the engine processes **each ingredient
independently**. For one ingredient, the events are:

- **manual stock changes** (`add` / `remove`) at their `at`
- **covering trips**: trips whose sections include the ingredient's shop
  section, at the trip's `at`
- **extra purchases**: trips that don't cover the section but have recorded
  purchases of the ingredient, at the trip's `at`. For example, a shopper might
  buy ice cream on a "no freezer" trip. **Recorded purchases always count**,
  whatever the trip's sections.
- **mealtimes that consume it**, at the mealtime's `at`

Only covering trips take part in shopping-list planning: they end a shopping
window, and while planned they're assumed to buy their list. An extra purchase
only adds what was recorded. It never ends another trip's window, and nothing
beyond the recorded quantity is ever assumed of it.

Events are sorted by:

1. `at`, ascending
2. type rank: manual = 0, covering trip or extra purchase = 1, mealtime = 2. So
   a trip at 17:00 supplies a dinner at 17:00, and stock brought "at 17:00" is
   there for both.
3. a deterministic tie-break: manual by `id`; trips by `id`; mealtimes by meal
   `name`, then mealtime `id`. This only decides which of Dinner A and Dinner B
   reports a shortfall when both run short.

### 3.5 The walk

For each ingredient, walk the sorted events with `balance = 0`:

#### Manual add

`balance += quantity`.

#### Manual remove

```plain
taken = min(quantity, balance); balance -= taken
if quantity - taken > EPSILON: warning 'removed-more-than-stock'
```

#### Mealtime

```plain
need = consumption; available = balance
if need - available > EPSILON:
  shortfall { needed: need, available, missing: need - available, past: at < now }
  balance = 0
else:
  balance -= need
```

#### Extra purchase

`balance += recorded`, whatever the trip's status. The trip's shopping list
gets the line `{ listQuantity: 0, recordedQuantity: recorded }`, so the
shopper sees the extra item they recorded.

#### Covering trip, status `done`

`balance += recorded` (the sum of this trip's purchases of the ingredient).

#### Covering trip, status `planned`

1. **Window:** the events after this trip, up to but not including the next
   **covering** trip for this ingredient (or the end). Extra purchases inside
   the window don't end it.
2. **Required purchase:** walk the window from the current balance, tracking
   the running net outflow:

   ```plain
   out = 0; peak = 0
   for e in window:
     manual add:      out -= quantity
     extra purchase:  out -= recorded
     remove:          out += quantity
     mealtime:        out += consumption
     peak = max(peak, out)
   listQuantity = max(0, peak - balance)
   ```

   `peak` is the most the window ever draws down below its starting balance, so
   buying `listQuantity` is the least that avoids any shortfall in the window.
   Removals count as outflow here: if someone has planned to give food away,
   the list covers it. An extra purchase in the window reduces the list by what
   was actually bought, and by nothing more.
3. **Contribution:** `balance += max(listQuantity, recorded)`. While shopping,
   buying more than listed counts at once. Buying less is still assumed to be
   made up until the trip is finished.
4. **Shopping list line:** emit `{ listQuantity, recordedQuantity: recorded }`
   if either is greater than zero.

For a `done` covering trip, the line is `{ listQuantity: <computed as above>,
recordedQuantity }`. The finished list still shows what was planned against
what was bought, but only `recorded` moves stock.

Example of an extra purchase not ending a window:

- Facts: Pantry trip P1 (planned) on Jan 1; "corner dairy" trip C on Jan 2,
  covering only Dairy and Bakery, with 1 can of beans recorded; a dinner on
  Jan 3 needing 10 cans; no other Pantry trip; no beans in stock.
- P1's window runs to the end, past C. It contains C's extra purchase
  (`out = -1`) and the dinner (`out = 9`), so `peak = 9` and P1's list says
  9 cans.
- C contributes exactly 1 can, whether it's planned or done, and there's no
  shortfall.

#### Worked example

- Facts: beans in stock 1 can; trip T at Jan 1 10:00 covers Pantry;
  mealtimes need 3 cans (Jan 1 dinner) and 2 cans (Jan 2 lunch); the next
  Pantry trip is Jan 3.
- At T, the window is the two mealtimes: `peak = 5`, `balance = 1`, so
  `listQuantity = 4`. This matches the brief.

### 3.6 Warnings

```ts
type Warning =
  | { code: 'meal-without-recipe'; mealId: string }                 // only if a mealtime is ≥ now
  | { code: 'mealtime-without-attendees'; mealId: string; mealtimeId: string }
  | { code: 'missing-recipe'; mealId: string; recipeId: string }
  | { code: 'missing-ingredient'; ingredientId: string; recipeId?: string; stockChangeId?: string }
  | { code: 'removed-more-than-stock'; stockChangeId: string; ingredientId: string; excess: number }
  | { code: 'trip-not-finished'; tripId: string }                   // planned and at < now
  | { code: 'outside-holiday-dates'; mealId?: string; tripId?: string; stockChangeId?: string };
```

### 3.7 Performance

- Expected size per holiday: about 100 mealtimes, 10 trips, 200 stock
  changes and 300 ingredients.
- The whole plan is recomputed from scratch on every change, with no
  incremental update. The windowed walk is linear per ingredient, so a full
  plan takes well under a few milliseconds.
- If profiling ever shows otherwise, memoise per-ingredient results.

## 4. DynamoDB storage

Table `meal-planner-<env>-data`: on-demand billing, point-in-time recovery on,
deletion protection on in prod, server-side encryption with an AWS-owned key.

| Attribute  | Type | Notes                                                                                  |
| ---------- | ---- | -------------------------------------------------------------------------------------- |
| `PK`       | S    | Partition key                                                                          |
| `SK`       | S    | Sort key                                                                               |
| `type`     | S    | `holiday`, `member`, `attendee`, `meal`, `trip`, `stockChange`, `recipe`, `ingredient` |
| `GSI1PK`   | S    | Member items only: `USER#<sub>`                                                        |
| `GSI1SK`   | S    | Member items only: `HOLIDAY#<holidayId>`                                               |
| *(fields)* |      | The domain fields from [§2.2](#22-stored-facts), top-level, camelCase                  |

| Item          | PK             | SK                |
| ------------- | -------------- | ----------------- |
| Holiday       | `HOLIDAY#<id>` | `META`            |
| Member        | `HOLIDAY#<id>` | `MEMBER#<sub>`    |
| Attendee      | `HOLIDAY#<id>` | `ATTENDEE#<id>`   |
| Meal          | `HOLIDAY#<id>` | `MEAL#<id>`       |
| Shopping trip | `HOLIDAY#<id>` | `TRIP#<id>`       |
| Stock change  | `HOLIDAY#<id>` | `STOCK#<id>`      |
| Recipe        | `CATALOGUE`    | `RECIPE#<id>`     |
| Ingredient    | `CATALOGUE`    | `INGREDIENT#<id>` |

**GSI `gsi1`** (`GSI1PK`, `GSI1SK`, keys-only projection) lists a user's
holidays.

### Access patterns

| Pattern                           | Operation                                                             |
| --------------------------------- | --------------------------------------------------------------------- |
| Load a holiday                    | `Query PK = HOLIDAY#<id>` (paginated)                                 |
| Check membership                  | `GetItem PK = HOLIDAY#<id>, SK = MEMBER#<sub>`                        |
| My holidays                       | `Query gsi1 GSI1PK = USER#<sub>`, then `BatchGetItem` of each `META`  |
| Count members (last-member check) | `Query PK = HOLIDAY#<id>, begins_with(SK, "MEMBER#")`                 |
| Load the catalogue                | `Query PK = CATALOGUE` (paginated)                                    |
| Create item                       | `PutItem` with `attribute_not_exists(PK)`; `version = 1`              |
| Update item                       | `PutItem` with `version = :expected`; stored `version = expected + 1` |
| Delete item                       | `DeleteItem` (unconditional; idempotent)                              |
| Delete a holiday                  | Query the partition, then `BatchWriteItem` deletes in 25s             |
| Create a holiday                  | `TransactWriteItems`: `META` + the creator's `MEMBER`                 |

#### Sizing

- The largest item is a long generic meal: 30 mealtimes × 10 attendees,
  about 15 KB. That is far under the 400 KB limit.
- The catalogue partition is a single "hot" key. At this scale (a handful of
  users) that's irrelevant.

## 5. API

Defined in `terraform/module/meal-planner/openapi.yaml` (OpenAPI 3.0) and
imported into an API Gateway REST API:

- request validators on bodies and parameters
- a Cognito user-pool authorizer on every route
- `AWS_PROXY` Lambda integrations

The frontend generates its types with `openapi-typescript` (`make api-types`).

All paths are under `/api`, served through CloudFront.

### 5.1 Routes

| Method & path                                        | Lambda      | Body → Response                                                          |
| ---------------------------------------------------- | ----------- | ------------------------------------------------------------------------ |
| `GET /api/holidays`                                  | `holidays`  | → `{ holidays: Holiday[] }`                                              |
| `PUT /api/holidays/{holidayId}`                      | `holidays`  | `HolidayInput` → `Holiday` (create also adds caller as member)           |
| `GET /api/holidays/{holidayId}`                      | `holidays`  | → `HolidayFacts & { members: Member[] }`                                 |
| `DELETE /api/holidays/{holidayId}`                   | `holidays`  | → `204`                                                                  |
| `PUT /api/holidays/{holidayId}/members/{userSub}`    | `holidays`  | `{ version: 0 }` → `Member`                                              |
| `DELETE /api/holidays/{holidayId}/members/{userSub}` | `holidays`  | → `204`, or `409 last-member`                                            |
| `PUT /api/holidays/{holidayId}/attendees/{id}`       | `holidays`  | `AttendeeInput` → `Attendee`                                             |
| `PUT /api/holidays/{holidayId}/meals/{id}`           | `holidays`  | `MealInput` → `Meal`                                                     |
| `PUT /api/holidays/{holidayId}/trips/{id}`           | `holidays`  | `TripInput` → `ShoppingTrip`                                             |
| `PUT /api/holidays/{holidayId}/stock-changes/{id}`   | `holidays`  | `StockChangeInput` → `StockChange`                                       |
| `DELETE /api/holidays/{holidayId}/{kind}/{id}`       | `holidays`  | → `204`; `kind` is one of `attendees`, `meals`, `trips`, `stock-changes` |
| `GET /api/catalogue`                                 | `catalogue` | → `Catalogue` (including soft-deleted items)                             |
| `PUT /api/catalogue/recipes/{id}`                    | `catalogue` | `RecipeInput` → `Recipe`                                                 |
| `PUT /api/catalogue/ingredients/{id}`                | `catalogue` | `IngredientInput` → `Ingredient`                                         |
| `DELETE /api/catalogue/{kind}/{id}`                  | `catalogue` | → `204`; sets `deleted: true` (and bumps `version`)                      |
| `GET /api/users`                                     | `users`     | → `{ users: { sub: string; name: string }[] }`                           |
| `GET /api/health`                                    | mock        | → `{ status: "ok" }`, no auth                                            |

**Request bodies (`*Input`):**

- Each is the item's domain fields plus `version`, without `id`,
  `updatedAt` or `updatedBy`.
- `version: 0` means "create". Any other value is the version the client last
  read.
- The server sets `updatedAt` and `updatedBy` from the JWT.

### 5.2 Validation

#### API Gateway schemas enforce

- required fields and field types
- string lengths: names 1–100 characters, notes ≤ 10,000 characters
- quantities and servings > 0
- the `ShopSection` and `MealSlot` enums
- `LocalDate` and `LocalDateTime` patterns, an IANA-looking time zone, and a
  UUID pattern on IDs
- array limits: 1–100 mealtimes per meal; ≤ 200 recipe lines

#### The Lambda additionally checks

- **Membership**, for every route under `/holidays/{holidayId}` except creating
  one.
- **Holiday doesn't exist yet**, before creating one. This is enforced by the
  transaction's conditions.
- **Last member:** removing a holiday's last member returns `409 last-member`.
- **Unique IDs within a meal:** mealtime IDs must be unique, as must attendee
  IDs within each mealtime.
- **Unique ingredients within a recipe:** each ingredient may appear in only
  one line.
- **Stock-change kind is fixed:** an update can't change the `kind`, or turn a
  purchase into a manual change or the reverse.

The Lambda deliberately doesn't check that referenced IDs exist. The engine
handles dangling references.

### 5.3 Errors

All errors use the shape `{ "error": { "code": string, "message": string } }`.

| Status | `code`             | When                                                            |
| ------ | ------------------ | --------------------------------------------------------------- |
| 400    | `validation`       | Schema or semantic validation failed                            |
| 401    | *(API Gateway)*    | Missing or invalid JWT                                          |
| 403    | `not-a-member`     | Caller isn't a member of the holiday                            |
| 404    | `not-found`        | Holiday doesn't exist                                           |
| 409    | `version-conflict` | Version mismatch; response includes `current` (the stored item) |
| 409    | `already-exists`   | Create (`version: 0`) of an ID that exists                      |
| 409    | `last-member`      | Removing the last member                                        |
| 500    | `internal`         | Anything else (details only in the logs)                        |

**Retries:** if a create times out and is retried, the retry gets
`already-exists`. In that case the client re-fetches the item and treats the
create as successful when the stored item matches what it sent.

## 6. Backend (Go Lambdas)

```plain
backend/
  cmd/
    holidays/main.go     # routes on (httpMethod, resource) from the proxy event
    catalogue/main.go
    users/main.go
  internal/
    auth/       # caller sub + name from requestContext.authorizer.claims
    httpx/      # JSON responses, error mapping
    model/      # structs mirroring §2.2, with JSON + dynamodbav tags
    store/      # all DynamoDB access: Get/Put/Delete with version conditions,
                # QueryPartition, membership check, transactions
    validate/   # semantic checks from §5.2
```

- **Runtime:** `provided.al2023`, arm64, 128 MB, 10 s timeout. Built by Make
  into `build/lambdas/<name>/bootstrap`, zipped, and deployed with
  `aws lambda update-function-code`, following the dnd-planner flow.
- **Configuration:** environment variables `TABLE_NAME`, plus `USER_POOL_ID`
  for `users`.
- **IAM (least privilege):**
  - `holidays`: `dynamodb:GetItem`, `PutItem`, `DeleteItem`, `Query`,
    `BatchGetItem`, `BatchWriteItem` and `TransactWriteItems` on the table and
    `gsi1`.
  - `catalogue`: `GetItem`, `PutItem` and `Query` on the table.
  - `users`: `cognito-idp:ListUsers` on the pool.
- **Logging:**
  - one structured JSON line per request: route, holiday ID, caller sub,
    status and duration
  - never item contents
  - 14-day retention
- **Users Lambda:** calls `ListUsers` (paginated) and returns `sub` and the
  `name` attribute, falling back to the email's local part. It never returns
  email addresses.

## 7. Frontend

### 7.1 Setup

- **SvelteKit:** `adapter-static` with `fallback: 'index.html'`. The root
  layout sets `ssr = false` and `prerender = false`; it's a client-only SPA.
- **Svelte:** Svelte 5 runes throughout.
- **Auth:** Amplify v6 `aws-amplify/auth` only, for sign-in, session refresh
  and tokens.
- **Search:** Fuse.js for fuzzy matching in pickers.
- **Strings:** all user-facing strings live in `src/lib/i18n/en.ts` (a typed
  message object) and are accessed through a `t()` helper. There's no runtime
  locale switching, but no hard-coded strings in components either.
- **Theme:** all colours, spacing and type are CSS custom properties in
  `src/lib/theme.css`, in light and dark variants. Components use only these
  variables.
- **Config:** Make writes `.env.<env>` from Terraform outputs
  (`VITE_USER_POOL_ID`, `VITE_USER_POOL_CLIENT_ID`). The API is always the
  relative `/api`.

  Overview.
- **Refresh:** a refresh button.

### 7.3 State

```plain
src/lib/stores/
  session.svelte.ts     # current user, tokens, sign-out
  catalogue.svelte.ts   # recipes + ingredients, loaded once per session, refetched on focus
  holiday.svelte.ts     # facts for the open holiday
  plan.svelte.ts        # plan = $derived(engine.plan(holiday.facts, catalogue, now))
  now.svelte.ts         # holiday-local "now", ticking every minute
```

**Writes** all go through a single `mutate()` helper in `holiday.svelte.ts` and
`catalogue.svelte.ts`:

1. Apply the change to the store optimistically, so the plan re-derives
   instantly.
2. `PUT` or `DELETE` with the item's current `version`.
3. On success, replace the item with the response (which has the new version).
4. On `409 version-conflict`, replace the item with `current` and show a toast
   naming the item, with a **Refresh holiday** action.
5. On a network error or `5xx`, retry with backoff up to 3 times. If that
   fails, roll back and show an error toast.

**Refetch** the holiday and catalogue on window focus (at most once every 30 s)
and on **Refresh**.

**Data per user:** the users list (`GET /users`) is cached for the session and
used to show member names.

### 7.4 Key views

#### Planner grid (`/plan`)

- **Layout:** rows are days from `startDate` to `endDate`; columns are the
  meal slots.
- **Mealtimes:** each mealtime is a chip showing the meal name, the recipe name
  (or *No recipe yet*), servings, and a red dot if it has a shortfall.
- **Generic meals:** a meal's mealtimes in consecutive rows of one column are
  joined into one vertical bar, so "Jan 1–5 Lunch" reads as one thing.
- **Parallel meals:** meals sharing a slot and day (Dinner A and Dinner B) sit
  side by side in the cell.
- **Adding meals:** an empty cell has a **+** that opens the meal editor
  prefilled with the slot, that date and the slot's default time.
- **Trips** are shown as markers between rows at their time.

#### Meal editor

- **Name:** suggested from the slot and dates ("Jan 1 Dinner", "Jan 1–5
  Lunch") until the user edits it.
- **Recipe:** a fuzzy picker, with an option to *create new recipe*, which
  opens the recipe editor and returns.
- **When:** a toggle between **One day** and **Several days**. The mealtime ID
  is kept stable when switching from one day to several.
  - *One day:* a date and time (defaulting to the slot time).
  - *Several days:* from date, to date and time. One mealtime is created per
    day.
- **Changing dates:** mealtimes for dates still in range are kept, with their
  IDs and attendees. New dates copy attendees from the nearest existing
  mealtime, or everyone if there are none.
- **Who's eating:**
  - for one day, a checkbox list of attendees with *Everyone* / *No one*
    shortcuts
  - for several days, a grid of mealtimes × attendees, with a whole-column
    toggle for "away for all of these" and a whole-row toggle per day
- **Preview:** the scaled ingredients from `plan.consumption` for the first
  mealtime, or a per-day table for a series. It updates live while editing.
- **Save** sends one `PUT` for the meal.

#### Recipe editor

- **Fields:** name, servings and notes.
- **Ingredient lines:** each is an ingredient picker plus a quantity, with the
  unit shown beside the quantity.
- **Keyboard flow:** Enter on the quantity adds a new line.
- **Usage:** a "Used in" list shows meals in the user's holidays that use the
  recipe. This is computed client-side from loaded holidays only, as a
  convenience, not a guarantee.

**Ingredient picker** (shared by recipes, stock and shopping):

- **Search:** fuzzy search over ingredients that aren't deleted.
- **Results:** shown as "Sugar · g · Pantry". Ingredients with the same name
  are adjacent.
- **Suggestions:** results from `data/common-ingredients.json` that aren't yet
  in the catalogue appear below, marked *Add to catalogue*.
- **Create new:** an inline form for name, unit and shop section. Unit
  suggestions are units already used for that name, then common units.
- **Duplicates:** creating a name + unit that already exists shows a warning.

#### Shopping mode (`/trips/[tripId]`, mobile-first)

- **Header:** the trip's name, time and covered sections, and a **Finish trip**
  button (or **Reopen trip** when done).
- **List:**
  - lines from `plan.shoppingLists[tripId]`, grouped by shop section in
    `SHOP_SECTIONS` order
  - within a section, sorted by name, then unit, so same-named ingredients are
    side by side
- **Each line** shows the name, the list quantity with unit, and a large
  **Got it** button.
  - Tapping **Got it** opens a quantity sheet prefilled with
    `listQuantity − recordedQuantity`, with ± buttons. Confirming `PUT`s a new
    `purchase`.
  - Recorded lines show a tick and the recorded quantity. Tapping edits or
    removes the purchase.
  - Lines not obtained are simply left. There's no "not obtained" state to
    record.
- **Add something else:** an ingredient picker that records a purchase not on
  the list.
- **Finishing a trip** whose lines still have unrecorded quantity shows a
  summary ("3 items not bought; this creates 2 shortfalls") before confirming.
  It sets `status: 'done'`.
- **Size and connectivity:** touch targets are at least 44 px. The page works
  from the loaded store; only the purchase writes use the network. A pending
  write shows a small spinner on its line.

#### Stock (`/stock`, mobile-first)

- **Now:** `stockAt(now)` for every ingredient with a non-zero balance or
  upcoming use, grouped by section.
- **Actions:** **Add** and **Remove** buttons, each with an ingredient picker,
  quantity, and time (defaulting to now) and an optional note.
- **History:** a timeline per ingredient from `plan.stock`, with assumed trip
  entries marked *planned*.
- **Unfinished trips:** if any `trip-not-finished` warnings exist, a banner
  says stock includes assumed purchases from those trips.

#### Overview (`/holidays/[holidayId]`)

- **Shortfalls:** upcoming shortfalls first, as cards:
  - each reads "Jan 3 Dinner: short 2 cans Beans"
  - each links to the meal, plus a *Add a trip before this* action that
    prefills a trip at the same date, 2 hours earlier
  - past shortfalls sit in a collapsed section
- **Warnings:** each warning has a direct link to fix it.
- **Next 48 hours:** a combined list of mealtimes and trips.

#### People (`/people`)

- **Attendees:** add, rename and delete.
  - Deleting an attendee assigned to mealtimes first lists them, then removes
    the attendee from those meals (a `PUT` per meal) before deleting.
- **Members:** add from `GET /users`, and remove.
  - Removing yourself asks for confirmation and returns you to `/`.

### 7.5 Login

- **Sign-in:** Amplify `signIn` with SRP.
- **First login:** admin-created users must set a new password first
  (`CONFIRM_SIGN_IN_WITH_NEW_PASSWORD_REQUIRED`). The login view handles this
  step inline.
- **Forgot password** uses Cognito's code-by-email flow.
- **Route guard:** unauthenticated visits to any route redirect to
  `/login?next=<path>`.

### 7.6 Accessibility

- **Markup:** semantic elements, every control labelled, and visible focus.
- **Pickers:** keyboard-operable combobox, following the WAI-ARIA combobox
  pattern.
- **Not colour alone:** shortfall and warning states use an icon and text as
  well as colour.
- **Planner grid:** a `table` with row and column headers. Chips are buttons.
- **Checks:** axe checks run in Playwright E2E tests.

## 8. Infrastructure

Terraform layout as in ARCHITECTURE.md. The `meal-planner` module contains the
pieces below.

### 8.1 CloudFront

- **Aliases:** `meal-planner.wildsea.lowe.kiwi` / `meal-planner-test.wildsea.lowe.kiwi`.
- **Certificate:** ACM, in us-east-1, DNS-validated in the existing
  `wildsea.lowe.kiwi` Route 53 zone.
- **Default behaviour:**
  - origin: the S3 bucket, private, via Origin Access Control
  - caching: the `CachingOptimized` policy
  - SPA routing: a **CloudFront Function** (viewer-request) rewrites any path
    without a file extension to `/index.html`. CloudFront's custom error
    responses aren't used, because they would also turn real API 403/404
    responses into the SPA.
- **`/api/*` behaviour:**
  - origin: the API Gateway stage
  - caching: the `CachingDisabled` policy
  - request headers: the `AllViewerExceptHostHeader` policy, which forwards
    `Authorization`
  - methods: all HTTP methods allowed
- **Response headers policy:**
  - HSTS
  - `X-Content-Type-Options`
  - `Referrer-Policy: strict-origin-when-cross-origin`
  - a CSP allowing `'self'` plus `cognito-idp.ap-southeast-2.amazonaws.com`
    for `connect-src`
  - `X-Frame-Options: DENY`
- **Inline bootstrap script:** `index.html` has SvelteKit's inline bootstrap
  `<script>`, which changes every build. The header's `script-src` therefore
  allows inline scripts, and SvelteKit's `csp` option (hash mode) adds a
  second CSP as a `<meta>` tag with that script's hash. Browsers enforce both,
  so only the hashed bootstrap runs.
- **Caching of uploads:** assets under `/_app/immutable/` are uploaded with
  `Cache-Control: public, max-age=31536000, immutable`. `index.html` is
  uploaded with `no-cache`.

### 8.2 API Gateway

- **API:** a REST API built from `openapi.yaml` (templated with the Lambda ARNs
  and user pool ARN), with a single stage named `api`.
- **Throttling:** 20 requests/s, burst 40.
- **Logging:** access logs to CloudWatch, 14-day retention.

### 8.3 Cognito

- **Sign-up:** `allow_admin_create_user_only = true`.
- **Sign-in:** by email; required attribute `name`.
- **Passwords:** at least 12 characters; MFA off.
- **App client:** public (no secret); SRP auth; refresh token valid 30 days.
- **Invitations:** Cognito's default email sends the temporary password.
  `make create-user ENV=test EMAIL=… NAME=…` wraps `admin-create-user`.

### 8.4 Other

- **S3 UI bucket:** private, versioned, with public access blocked and
  SSE-S3 encryption.
- **DynamoDB:** as in [§4](#4-dynamodb-storage).
- **Lambdas:** via the reusable `lambda` module, each with its own role and log
  group.
- **Tags:** `project = meal-planner` and `environment = <env>` on everything.

## 10. Testing

### Engine (Vitest)

This is where most of the testing goes. A `factsBuilder()` test helper
constructs holidays in a few lines. Required scenarios:

- **Scaling:**
  - recipe for 4 eaten by 8 doubles every quantity
  - 3 eaten by 2 gives fractional quantities, kept exactly
  - 0 attendees consume nothing and produce a warning
- **Brief example:** needs of 3 + 2 cans with 1 in stock gives a list of 4.
- **Windows:** a trip's list stops at the next trip covering the section, but
  not at a trip that doesn't cover it (for example, Frozen items on a
  no-freezer trip).
- **Tie ordering:**
  - a trip and a mealtime at the same time: the trip supplies the mealtime
  - Dinner A and Dinner B at the same time are deterministic
- **Manual changes:**
  - a manual add inside a window reduces the list
  - a manual remove increases it
- **Removing more than in stock** clamps the balance and produces a warning.
- **Planned trip:**
  - recorded quantity above the list counts at once
  - recorded quantity below the list is still assumed made up
- **Done trip:**
  - only recorded quantities count
  - an item not bought creates a shortfall before the next trip
- **Purchases outside the trip's sections:**
  - they still count, as exactly the recorded quantity
  - they don't end an earlier covering trip's window; the
    §3.5 corner-dairy example gives a list of 9 and no shortfall
  - nothing beyond the recorded quantity is assumed, whether the trip is
    planned or done
- **No trip covers the ingredient:** the mealtime has a shortfall.
- **Dangling references** (deleted attendee, trip, recipe or ingredient) are
  ignored, with the right warnings.
- **Last-minute changes:** a mealtime added before a trip changes that trip's
  list; one removed or moved past the next trip shifts the need to that trip.
- **Property test** (fast-check): for any facts, if every planned trip buys
  exactly its list, there are no upcoming shortfalls for ingredients covered
  by an earlier trip.

### Components (Vitest + Testing Library)

- ingredient picker: fuzzy match, create-new, duplicate warning
- meal editor: switching between one day and several days, date-range
  regeneration that keeps attendees
- shopping line: **Got it** flow

### Backend (Go)

- **Store:** table-driven tests against DynamoDB Local in Docker, covering:
  - version conditions
  - create conflicts
  - membership checks
  - last-member checks
  - holiday deletion paging
- **Handlers:** tested with a fake store.

### End to end (Playwright)

- **Against the dev server**, with the API mocked via route interception from
  fixture holidays: plan a meal, build a recipe, shop a trip at mobile
  viewport, and resolve a shortfall.
- **Smoke test against the test environment:** log in, open a seeded holiday,
  load the shopping list.
